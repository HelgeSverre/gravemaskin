# Research: BEPUphysics v2 from F#

> Produced by the gravemaskin research workflow, 2026-08-28.

## Summary

BEPUphysics v2 is the right physics engine for Gravemaskin, and the F#-hostile parts of its API are real but small and now empirically verified: I built and ran a minimal F# .NET 10 console app against BepuPhysics 2.5.0-beta.29 (project at /private/tmp/claude-501/-Users-helge-code-gravemaskin/376b6ec1-08db-425d-99a1-9e169d31de46/scratchpad/bepufs/Program.fs) implementing both struct-generic callback interfaces ([<Struct>] types implementing INarrowPhaseCallbacks and IPoseIntegratorCallbacks, including the SIMD-wide IntegrateVelocity(Vector<int>, Vector3Wide, QuaternionWide, BodyInertiaWide, Vector<int>, int, Vector<float32>, byref<BodyVelocityWide>) signature and the 'TManifold : unmanaged generic ConfigureContactManifold), creating a Simulation, adding statics/dynamics, wiring a Hinge + AngularAxisMotor "boom" driven by a kinematic anchor, retuning the motor live via Solver.ApplyDescription, and asserting a ball comes to rest at y=0.5. It works; the friction is limited to F#'s byref/inref pedantry (in-parameters need let-bound locals passed with &, C# out maps to byref here, struct constraint descriptions need `let mutable` + address-of, no `{ x with }` on structs).

BEPU2's constraint set maps almost one-to-one onto an excavator: Hinge for boom/stick/bucket/linkage pins, LinearAxisServo (position-target) or LinearAxisMotor (velocity-target) + PointOnLineServo for hydraulic cylinders, AngularAxisMotor for slew and track drive, and ServoSettings/MotorSettings expose exactly the hydraulic-like knobs — MaximumForce (impulse cap = relief-valve pressure × piston area), MaximumSpeed (flow-rate limit), BaseSpeed, and SpringSettings(frequency, dampingRatio) for compliance (oil/hose elasticity). The engine's own Tank demo is a ready blueprint for tracks (per-wheel LinearAxisServo suspension + PointOnLineServo + AngularHinge, AngularAxisMotor drive, adjacent wheels linked by zero-target-velocity AngularAxisMotors with MotorSettings(float.MaxValue, 1e-4) to fake a connected tread) and the RagdollDemo shows the collision-filter bitfield pattern needed to stop linked excavator parts colliding with each other. For deformable terrain, the recommended pattern is per-chunk static Mesh collidables rebuilt off the dug region (Statics remove/add or ApplyDescription with a new shape) with Tree.Refit/RefitAndRefine for small deformations; the CustomVoxelCollidableDemo shows a full custom IHomogeneousCompoundShape voxel collidable but the demo itself steers production users toward simpler representations. Determinism is per-machine (Simulation.Deterministic=true under IThreadDispatcher), which is fine for a single-player 60Hz fixed-step sandbox. JoltPhysicsSharp (MIT, active, .NET 10, NuGet 2.22.0, includes TrackedVehicleController bindings) is the only serious alternative — its tracked-vehicle controller is more turnkey — but it costs native binaries, GC-visible handle wrappers, no source-level debuggability, and a vehicle model tuned for gameplay rather than the force-level hydraulic realism this game wants. Stay pure-.NET with BEPU2.

## Key findings

- BEPU v2 status: Apache-2.0, pure C#, ~2000 commits, active; NuGet stable is 2.4.0 (Feb 2022) but the line to use is 2.5.0-beta.29 (Apr 2024, master is newer still) — betas are the de-facto current version (Stride ships on it); targets .NET 8+, restores and runs cleanly on .NET 10.0.400 on macOS arm64 (verified locally).
- F# struct-generic callbacks VERIFIED WORKING on 2.5.0-beta.29/.NET 10: [<Struct>] type implementing INarrowPhaseCallbacks (incl. generic member with constraints 'TManifold : unmanaged and 'TManifold : struct and 'TManifold :> IContactManifold<'TManifold>', PairMaterialProperties as byref not outref) and IPoseIntegratorCallbacks (SIMD-wide IntegrateVelocity taking Vector<int> bodyIndices, Vector3Wide, QuaternionWide, BodyInertiaWide, Vector<int> mask, Vector<float32> dt, byref<BodyVelocityWide>; precompute gravity*dt as Vector3Wide.Broadcast in PrepareForIntegration). Working file: /private/tmp/claude-501/-Users-helge-code-gravemaskin/376b6ec1-08db-425d-99a1-9e169d31de46/scratchpad/bepufs/Program.fs.
- F# friction points found by compiling: (1) BEPU APIs take 'in' (inref) parameters everywhere — Shapes.Add(&shape), Bodies.Add(&desc), Statics.Add(&desc), Solver.Add(a, b, &constraintDesc) — so every shape/description must be a let-bound local, you cannot pass constructor results inline; (2) constraint descriptions are structs, so no `{ x with }` — use `let mutable` and property assignment; (3) explicit interface implementation is fine because BEPU calls through generic constraints (constrained calls, still devirtualized/inlined).
- Full v2 constraint inventory (BepuPhysics/Constraints): BallSocket, BallSocketMotor, BallSocketServo, Hinge, SwivelHinge, AngularHinge, AngularSwivelHinge, AngularAxisMotor, AngularAxisGearMotor, AngularMotor, AngularServo, LinearAxisServo, LinearAxisMotor, LinearAxisLimit, PointOnLineServo, DistanceServo, DistanceLimit, CenterDistanceConstraint, CenterDistanceLimit, TwistServo, TwistMotor, TwistLimit, SwingLimit, Weld, AreaConstraint, VolumeConstraint, OneBodyAngularServo/Motor, OneBodyLinearServo/Motor. Everything an excavator linkage needs exists.
- Hydraulics mapping: a cylinder = LinearAxisServo (position target along LocalAxis) or LinearAxisMotor (velocity target — closer to valve-spool control) between rod-body and barrel-body, paired with PointOnLineServo to kill the two perpendicular DOFs, plus LinearAxisLimit for stroke ends. ServoSettings = {MaximumSpeed (hydraulic flow limit), BaseSpeed, MaximumForce (relief-valve force cap, applied as impulse = MaximumForce*dt per substep)}; MotorSettings = {MaximumForce, Softness=1/damping}. SpringSettings(frequency Hz, dampingRatio) gives compliance; keep frequency <= half the substep rate (~30 for 60Hz, higher with substeps).
- Tank demo (Demos/Demos/Tanks/Tank.cs + TankController.cs) is the track blueprint: per wheel — LinearAxisServo as suspension spring (SpringSettings(30,1), TargetOffset = suspension length), PointOnLineServo to constrain wheel travel to the suspension line, AngularHinge for the spin axis, AngularAxisMotor for drive; tread faked by chaining adjacent wheels with AngularAxisMotor(target=0, MotorSettings(float.MaxValue, 1e-4)) so drive torque distributes across the tread; control code only touches constraints when input changes to avoid waking the vehicle every frame; turret/barrel = Hinge attachment + TwistServo aiming — the same pattern works for excavator slew.
- RagdollDemo shows the standard pattern for articulated bodies: per-body bitfield collision groups checked in INarrowPhaseCallbacks.AllowContactGeneration to disable collision between directly-linked bodies (boom vs stick vs cylinders) while keeping bucket-vs-chassis collision live.
- Deformable terrain collision: v2 has no Terrain type (v1 did). Mesh is a static-friendly shape whose Tree can be refit in place — DemoMeshHelper.CreateDeformedPlane + Mesh constructors that take pre-ordered triangles with an unbuilt tree, then Tree.Refit / Tree.RefitAndRefine(pool, ...) (multithreaded variant exists) for deformation without full rebuild; for topology changes (digging holes) recreate the chunk's Mesh and swap via Statics ApplyDescription/remove+add. Mesh/Tree have Serialize/GetSerializedByteCount (a forum user cut terrain load from 5s to 50ms). CustomVoxelCollidableDemo demonstrates a full custom IHomogeneousCompoundShape<Box,BoxWide> voxel collidable with its own collision tasks, but the demo text itself says the tree-over-regular-grid representation is suboptimal for production voxel worlds.
- Determinism: deterministic run-to-run on one machine if single-threaded, or multithreaded with Simulation.Deterministic=true (small perf cost, default false). NOT cross-platform/cross-CPU deterministic (no soft-float/fixed-point path). Threading via user-supplied IThreadDispatcher (BepuUtilities.ThreadDispatcher reference impl); guidance: leave one core free to avoid frame spikes. Perf headroom is enormous for this game's scale — BEPU2 demos push 10k-100k+ bodies; an excavator (≈15-25 bodies, ≈30 constraints) plus a few hundred rock/clod rigid bodies and dozens of static chunk meshes is trivial at 60Hz with substepping (SolveDescription(velocityIterations, substeps), e.g. (8,4) for stiff linkages).
- JoltPhysicsSharp: MIT, amerkoleci, active (485+ commits), NuGet 2.22.0, targets .NET 9/10, binds Jolt via the joltc C wrapper with prebuilt natives; recently added VehicleTrack/VehicleConstraint bindings (PR #137), so Jolt's TrackedVehicleController (built for tanks/bulldozers: engine, transmission, tracks, wheel casts, suspension) is reachable from C#/F#. Costs: native interop layer (harder debugging, macOS arm64 native binary dependency), class-based handle wrappers (GC pressure at the boundary), maintainer prioritizes features via sponsorship, and the vehicle controller is a gameplay-grade black box — you can't model individual hydraulic cylinders with it anyway; excavator arm still needs raw constraints either way.
- Runtime constraint retuning verified: Solver.ApplyDescription(handle, &desc) mid-run changes motor target velocity/max force — this is the per-frame hydraulic control path (joystick -> valve model -> per-tick TargetVelocity/MaximumForce updates). Guard writes behind change detection like TankController does, or the machine never sleeps.

## Recommendations

- Pick BEPUphysics 2.5.0-beta.29 (or current master via NuGet prerelease) over JoltPhysicsSharp. Rationale: pure managed = single-binary cross-platform desktop with zero native packaging on macOS/Windows/Linux, source-steppable from the F# debugger, and the excavator's core requirement — force-limited hydraulic actuators on an articulated linkage — is exactly BEPU's servo/motor constraint model; Jolt's advantage (turnkey TrackedVehicleController) doesn't cover the arm, and tracks are already solved by porting the Tank demo pattern.
- Excavator rig (concrete constraint graph): chassis(dynamic, real COM via offset compound) --Hinge(Y)+AngularAxisMotor--> house; house --Hinge(pin)--> boom --Hinge--> stick --Hinge--> bucket via the H-link/dog-bone as 2 extra small bodies with BallSocket/Hinge pins; each hydraulic cylinder = 2 bodies (barrel+rod) joined by PointOnLineServo + LinearAxisMotor (velocity mode, TargetVelocity from valve spool, MaximumForce from circuit pressure x piston area, different extend/retract force for rod-side area) + LinearAxisLimit for stroke; cylinders pin to boom/stick with Hinge or BallSocket. Disable collision within the linkage via a bitfield CollidableProperty checked in AllowContactGeneration (RagdollDemo pattern).
- Tracks: copy the Tank demo verbatim first (per-wheel LinearAxisServo suspension + PointOnLineServo + AngularHinge + AngularAxisMotor, adjacent wheels chained with AngularAxisMotor(0, MotorSettings(maxValue, 1e-4))); skid-steer by differential left/right target velocities. Defer any real track-link simulation — the demo approach reads correctly on soft terrain once you add per-contact friction from the soil model.
- Terrain collision: chunked static Mesh per soil chunk (matching your render chunking). On dig: remesh the chunk surface (marching cubes/dual contouring off the SDF), build the Mesh with the pre-ordered-triangle constructor + RefitAndRefine (multithreaded), then swap the static's shape (Statics.ApplyDescription or Remove+Add; also Shapes.RecursivelyRemoveAndDispose the old one to avoid pool leaks). Do NOT use compound-of-boxes voxel collision for the surface, and skip the CustomVoxelCollidableDemo route for v1 — it's a lot of custom collision-task registration for marginal gain. Loose soil clods = small convex hulls/spheres as regular dynamics; settled soil converts back to the chunk mesh and the bodies are removed.
- F# integration boundary (matches Ironsight's functional-core/imperative-shell): keep Domain.fs pure (machine state as records: joint angles, cylinder extensions, valve commands, soil deltas). Add Physics.fs owning a single mutable PhysicsWorld class/record-of-mutables: BufferPool, Simulation, ThreadDispatcher, handle tables (Dictionary<EntityId, BodyHandle>, constraint handles per cylinder/motor). Per 60Hz tick: (1) pure step computes ActuatorCommands from input+domain state; (2) Physics.apply world commands writes TargetVelocity/MaximumForce via ApplyDescription (change-guarded); (3) Simulation.Timestep(1f/60f, dispatcher); (4) Physics.readback returns an immutable snapshot (poses, velocities, cylinder extensions measured from body pairs, contact impulses for tip-over/soil forces) that the pure layer folds into the next domain state. Renderer reads only the snapshot. Physics.fs is the only file that touches BepuPhysics types besides thin shape helpers.
- Set Simulation.Deterministic <- true and use a fixed thread count for reproducible same-machine replays (matches your prior games' deterministic 60Hz style); accept that replays are not portable across CPUs and don't design features that need cross-machine determinism.
- Use SolveDescription(8, 4) (8 velocity iterations, 4 substeps) as the starting point — stiff heavy linkages (multi-tonne bucket on long lever arms with high mass ratios) need substepping; with 4 substeps the effective rate is 240Hz so SpringSettings frequencies up to ~120 are stable, letting cylinders feel rigid.
- Wrap the byref ceremony once in a small GlUtil-style module (e.g. Bepu.fs): inline helpers `addStatic sim shape pose`, `addDynamic sim shape mass pose`, `addConstraint sim a b desc`, `retune sim handle desc` that do the let-binding/address-of internally so gameplay code stays clean.
- Soil-machine force coupling: get bucket dig forces by opposing contact impulses — either read accumulated impulses from the solver or via INarrowPhaseCallbacks/ContactEventsDemo-style collection — and feed them into the soil sim as cut/failure forces; conversely apply soil resistance to the bucket as a OneBodyLinearMotor/direct ApplyImpulse each tick. Keep this exchange inside Physics.fs so the pure soil model sees only numbers.
- Start the repo with the verified scaffold: copy /private/tmp/claude-501/-Users-helge-code-gravemaskin/376b6ec1-08db-425d-99a1-9e169d31de46/scratchpad/bepufs/Program.fs's callback structs into Physics.fs as-is — they are the exact signatures for 2.5.0-beta.29 on .NET 10 and took several compile iterations to get right.

## Risks

- Version drift: NuGet 'stable' 2.4.0 is from Feb 2022 and its callback signatures differ from 2.5 betas (e.g. AllowContactGeneration gained ref float speculativeMargin, ConfigureContactManifold's TManifold constraint changed to unmanaged, IntegrateVelocity went fully vectorized). Any snippet found online may target the wrong version — pin 2.5.0-beta.29 and match signatures against the installed package, not docs.
- The vectorized IPoseIntegratorCallbacks.IntegrateVelocity operates on SIMD lanes of multiple bodies; per-body custom forces (e.g. per-clod drag) inside it require masked wide operations — awkward in F#. Prefer applying per-body forces via bodyReference.ApplyImpulse before Timestep instead of inside the integrator callback.
- BufferPool lifetime leaks: Simulation does not own its allocator; forgetting Simulation.Dispose/pool.Clear, or dropping replaced chunk Mesh shapes without Shapes.RecursivelyRemoveAndDispose, leaks unmanaged buffers. Centralize all create/destroy in Physics.fs.
- Frequent static Mesh swaps have a broadphase/refit cost: swapping many chunks the same tick (big cave-in) will spike; budget N chunk swaps per tick and queue the rest. Tree.Refit only handles deformation of existing triangles — topology changes force a rebuild of that chunk's mesh.
- Waking discipline: writing constraint descriptions every frame keeps the machine and everything it touches permanently awake and kills the 'extremely low cost sleep' advantage; also a sleeping excavator won't respond to soil settling under it — copy the TankController change-guard pattern and explicitly wake when needed.
- Stiffness cliffs: mass ratios (20t chassis vs 50kg linkage dog-bone) and SpringSettings frequency above ~half the substep rate cause jitter/explosion; keep linkage part masses artificially reasonable (BEPU docs suggest <~10:1 ratios across constraints) and tune frequency to the substepped rate, not 60Hz.
- Determinism is same-machine only; multithreaded determinism requires Deterministic=true AND a stable thread dispatcher — changing core counts changes results. Don't promise replay files that survive a hardware change.
- F# assert (System.Diagnostics.Debug.Assert) is compiled out in Release — the scratch test's assertion style must become real tests (Expecto/xUnit or a plain exit-code check) in the game repo.
- If JoltPhysicsSharp is reconsidered later: its API surface follows sponsor demand, tracked-vehicle bindings are new (PR #137, 2025) and thin, and debugging crosses a managed/native boundary — budget for reading joltc source. Also Jolt's cross-platform determinism claims apply to identical binaries/compilers, not to arbitrary .NET hosts.
- OpenGL 4.1 macOS ceiling doesn't touch physics, but don't plan GPU-assisted collision/SDF work on compute shaders for the mac build — physics must stay CPU-side (BEPU is CPU-only anyway, so this aligns).
