# Research: .NET / F# High-Performance Simulation

> Produced by the gravemaskin research workflow, 2026-08-28.

## Summary

F#/.NET 10 can hit the 60Hz bar for this game, but only with a strict data-oriented core: flat struct arrays inside a chunked soil volume, zero steady-state allocation on the sim path, and a persistent worker pool with deterministic chunk partitioning. F# 9/10 close most of the historical perf gaps (struct DUs with shared field layout, struct equality without boxing, [<Struct>] optional params, InlineIfLambda for closure-free higher-order code, full Span/byref support since F# 4.5 plus `allows ref struct` generics in F# 9). What remains awkward vs C#: no ref fields in byref-like structs, byref-like values can't cross closures/async, and idiomatic F# (Seq, list, non-struct tuples, non-inlined lambdas) allocates — so the 60Hz core must be written in the "imperative shell inside functional module boundaries" style Ironsight already uses: for-loops over arrays of `[<Struct; IsReadOnly>]` records, mutation via byref/index, purity at the module API level, not per element.

On Apple Silicon, System.Numerics.Vector<T>/Vector128<T> map to NEON (128-bit — 4 floats wide, not 8 as on AVX2 x64), and System.Runtime.Intrinsics.Arm.AdvSimd is fully available; BEPUphysics2 is built on Vector<T> so it runs vectorized on M-series but at half the lane width of AVX2 machines. Realistic throughput reasoning: a simple settle/flow kernel (~20–50 ALU ops + ~32B memory traffic per cell) sustains roughly 5–20M cell-updates/sec/core scalar and 20–80M with SIMD; memory bandwidth is not the first ceiling at these sizes (2M cells × 32B × 60Hz ≈ 4GB/s vs ~100+GB/s on M-series). The documented .NET reference point is Saket.Particles: ~2M simple particles at 60fps (SIMD + multithreaded SoA on a Ryzen 2700X). Budget accordingly: ≤ ~1–2M *active* soil cells touched per tick across workers, 50–100k custom loose-soil particles, and only ~1–3k of those promoted to real BEPU rigid bodies at once. GC strategy: workstation concurrent GC + SustainedLowLatency, allocate all sim arrays once at startup (LOH is fine for one-time allocations), pool everything else (ArrayPool + BEPU's unmanaged BufferPool), and treat any per-frame allocation as a bug — real-world reports show default GC pauses of 20–55ms that no latency mode reliably fixes; the only winning move is not to allocate.

## Key findings

- F# language support level (F# 9/10, .NET 10): byref returns since F# 4.1; Span<T>/byref-like structs since F# 4.5 with strong lifetime checks; F# 9 adds `allows ref struct` generic anti-constraint consumption (can pass Span to modern BCL generics) and struct-DU memory-layout sharing (same-name/same-type fields across cases share storage) plus fixed struct-equality boxing in Array.contains/exists etc.; F# 10 adds [<Struct>] optional parameters (ValueOption, no heap alloc) and CE tail-calls. Still missing vs C#: ref fields inside byref-like structs (open suggestion fslang-suggestions#1143), byref-like values cannot be captured by closures/async/local functions (suggestions #805/#887), no scoped/ref-struct interfaces.
- InlineIfLambda (F# 6+) inlines lambda parameters regardless of size, eliminating closure allocations in higher-order hot-loop helpers; warning 3517 (<WarnOn>3517</WarnOn>) verifies call sites actually flatten. This is how you keep functional-looking iteration APIs (e.g. `Soil.iterActive`) allocation-free.
- Allocation traps in idiomatic F#: Seq/list combinators, non-struct tuples not consumed immediately (compiler detuples only when not first-class and often only when inlined), non-inlined lambdas, string formatting, boxing of structs through interface/equality paths, partial application. Fixes: [<Struct; IsReadOnly>] records, struct tuples for >1 return (or outref), voption, for-loops over arrays, `inline` + InlineIfLambda, avoid ValueTuples >16 bytes copied repeatedly.
- Apple Silicon SIMD: System.Runtime.Intrinsics.Arm.AdvSimd + AdvSimd.Arm64 expose ~360 NEON intrinsics; Vector128<T> is the portable sweet spot (maps to NEON on arm64, SSE on x64); Vector<T> is 128-bit on ARM64 — code tuned for 8-wide AVX2 runs 4-wide on M-series. .NET 8+ auto-vectorizes some memory ops and did major arm64 codegen work (consecutive-register allocation for NEON table lookups).
- BEPUphysics2: solver fully vectorized over Vector<T>, AoSoA constraint layout, memory-bandwidth-bound at high core counts; statics/inactive bodies nearly free (LotsOfStatics: <350µs/frame with 8 threads on a 3770K). Determinism: single-threaded runs are deterministic given identical interaction order; deterministic multithreaded mode exists (same thread count required); cross-platform (x64 vs arm64) determinism is explicitly NOT provided. Solver cost linear in iteration count; 1 velocity iteration + substepping is the recommended sweet spot. Thread oversubscription causes solver spikes — leave cores for your soil jobs.
- GC reality check: default GC max pauses reported at 20–55ms on small machines (dotnet/runtime#65850); SustainedLowLatency did NOT improve max pause there; LowLatency reduced pauses but ~10x RSS growth; game devs in dotnet/runtime discussion #115627 report mode-juggling and occasional large stutters as the best achievable. SustainedLowLatency suppresses foreground Gen2 (background Gen2 still runs). Conclusion echoed by XNA-era numbers (14ms GC for 100k live objects): zero-allocation steady state is the only robust strategy; GC.TryStartNoGCRegion is available for critical windows; force collections only on load screens.
- Data layout: SoA per chunk beats AoS when kernels touch a subset of cell properties (settle touches density/moisture/compaction but not material); SoA also enables SIMD and prefetching (vittorioromeo particle benchmark, HPC literature). Chunked flat arrays (e.g. 32^3 chunks) with an active/dirty chunk list keep the touched set small; run-length-encoded columns pay off only for storage/serialization, not for the hot update path — decode to flat on activation.
- Throughput budget reasoning: soil cell packed to 8–16B (material:byte, density:byte, moisture:byte, compaction:byte, flags, etc.) → 2M active cells/tick ≈ 32–64MB traffic ≈ 2–4GB/s at 60Hz, far under M-series bandwidth (~100–200GB/s package); the binding constraint is ALU/branchiness: ~5–20M cell-updates/s/core scalar, 4x-ish with NEON, so ~1–2M active cells/tick across 4–6 P-cores is a defensible ceiling with headroom. Best documented .NET particle figure: ~2M particles @60fps (Saket.Particles, SIMD+MT SoA); with terrain collision and clumping, budget 50–100k loose-soil particles in a custom SoA integrator, promoting only ~1–3k to BEPU rigid bodies (spheres/compounds) for machine interaction.
- Parallelism/determinism: per-frame Parallel.For allocates and has nondeterministic reduction order; use a persistent worker pool — simplest is to reuse BEPU's IThreadDispatcher for your own jobs. Determinism recipe: fixed chunk→worker partitioning by chunk index (not work stealing), checkerboard/red-black or double-buffered settle passes so neighboring chunks never race, ordered command buffers for cross-chunk particle transfers merged in a deterministic single-threaded phase.
- Profiling on macOS: no ETW — EventPipe replaces it: dotnet-trace collect --profile cpu-sampling --format speedscope → speedscope.app or Firefox Profiler; GC events via dotnet-trace gc-collect / dotnet-counters. samply (mstange) profiles native+managed on macOS with Firefox Profiler UI (run `samply setup` once; can't attach to Apple-signed binaries, your own are fine). Instruments/xctrace works for native-side (GL driver, memcpy) but managed frames need perf-map symbol resolution. BenchmarkDotNet with [MemoryDiagnoser] + DisassemblyDiagnoser for kernels; BDN's EventPipeProfiler exports .nettrace per benchmark.
- Prior-art fit: fsharp-of-duty (Ironsight) already uses deterministic fixed 60Hz functional-core/imperative-shell with Domain.fs/Sim.fs/Renderer.fs/GlUtil.fs and a test suite driving the sim headless — the soil pipeline should follow the same shape: Sim owns plain arrays, Renderer consumes dirty-chunk mesh jobs, tests run the sim without GL.

## Recommendations

- Runtime config (fsproj/runtimeconfig): <ServerGarbageCollection>false</ServerGarbageCollection>, <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>, set GCSettings.LatencyMode <- GCLatencyMode.SustainedLowLatency at startup, <TieredPgo>true</TieredPgo> with a warmup pass (run ~120 sim ticks + render a few frames before gameplay so tier-1 JIT happens off-screen). Add an in-game frame-time HUD (Stopwatch, p50/p95/p99 + GC.CollectionCount deltas per gen) from day one.
- Soil volume: 32^3 chunks of SoA flat arrays; pack cell state into 8–16 bytes total across parallel arrays (byte material, byte density, byte moisture, byte compaction, byte flags, i16 temperature/reserved); allocate all chunks' arrays once (or pool chunk buffers via ArrayPool/own free-list); maintain an active-chunk list and only run settle/flow kernels on dirty chunks; cap active cells per tick at ~1–2M and amortize (process K dirty chunks per tick, round-robin) — settling doesn't need to complete in one frame.
- Write the hot kernels as F# modules over arrays: `[<Struct; IsReadOnly>]` records, for-loops with byref/index mutation, `inline` + [<InlineIfLambda>] for any higher-order helpers, <WarnOn>3517</WarnOn> in the sim project to catch un-flattened lambdas, voption/struct tuples at API boundaries, zero Seq/list in Sim.fs. Keep the functional-core purity at the tick boundary (SimState in → SimState out) not per cell — same pattern as Ironsight.
- SIMD: write kernels against Vector128<float32>/Vector128<byte> (portable NEON/SSE) with a scalar tail, not Vector<T> (width surprises) and not raw AdvSimd unless a specific NEON op (pairwise add, table lookup) is proven needed. Byte-packed cells mean one Vector128 load processes 16 cells' worth of a property — big win for settle passes.
- Loose soil: custom SoA particle system (positions/velocities/materialId in parallel float arrays), integrated + collided against the soil SDF/heightfield on your own worker jobs; budget 50–100k particles. Promote only the particles that must push the machine (in bucket, under tracks) to BEPU bodies (sphere clumps), cap ~1–3k live BEPU dynamics, demote/merge aggressively back to volume. Never make every dirt particle a rigid body.
- BEPU setup: one Simulation, substepping (e.g. 2–4 substeps @60Hz outer tick) with 1 velocity iteration; excavator as bodies + constraints (hydraulics as motorized prismatic/linear axis constraints with force limits = cylinder force caps); tracks as several box/capsule contact patches, not per-link chains, until proven insufficient. Give BEPU a thread dispatcher with N-2 threads and run soil jobs on the same dispatcher after physics, or interleave; enable BEPU's deterministic mode and pin thread count for reproducible replays on the same machine — do not promise cross-platform determinism.
- Parallel soil jobs: fixed chunk→worker assignment (chunkIndex % workerCount), red-black checkerboard passes for neighbor-writing kernels, per-worker command buffers (particle spawns, chunk dirty marks, cross-chunk moves) merged in deterministic order on the main thread. Skip TPL Parallel.For/PLINQ in the tick path.
- Meshing: surface nets/marching cubes per dirty chunk on worker threads into pooled vertex buffers; OpenGL 4.1 has no persistent-mapped buffers (4.4) and no compute shaders — use glBufferData orphaning or a ring of VBOs, and accept that all soil sim is CPU-side on macOS.
- Profiling workflow: BenchmarkDotNet project (Benchmarks/) for kernels with MemoryDiagnoser (any B/op > 0 in a sim kernel fails review); dotnet-trace + speedscope for whole-game CPU; samply for mixed managed/native; assert zero Gen0 collections across 1000 headless sim ticks in a test (GC.CollectionCount before/after) — cheapest regression gate for the alloc-free invariant.
- Perf budget proposal @60Hz (16.67ms frame, target ≤12ms p99 total, Apple M-series, sim on 4–6 P-cores): Input+controls 0.1ms; Hydraulics/linkage force model 0.3ms; BEPU step (machine ~30 bodies/constraints, rocks ~200 mostly sleeping, ≤3k soil-clump dynamics, substepped) 2.5–4.0ms; Soil volume edits (bucket cut SDF ops, dirty marking) 0.3–0.8ms; Loose-particle update (≤100k, SoA, workers) 1.5–2.5ms; Settling/compaction (amortized K chunks/tick) 0.5–1.0ms; Chunk remesh (workers, amortized, budgeted queue) 1.0–2.0ms; Render submit (GL 4.1, orphaned buffers) 2.0–3.0ms; Audio/UI/misc 0.5ms; GC + OS jitter reserve ≥2.0ms. Systems marked 'amortized' must degrade by deferring work, never by blowing the frame.

## Risks

- GC pauses are the #1 frame-spike hazard: real reports show 20–55ms max pauses under default settings and SustainedLowLatency not improving worst case; any steady-state allocation in the 60Hz path will eventually hit Gen2/background GC stutter. Treat 0 B/frame as an invariant with a test, not a goal.
- Vector<T> is 128-bit on Apple Silicon: BEPU2 and your kernels get 4-wide floats, not 8-wide — perf numbers from x64/AVX2 benchmarks (including BEPU's own demos) roughly halve; budget against M-series measurements, not blog numbers from Ryzen/Intel.
- macOS OpenGL 4.1 ceiling: no compute shaders, no SSBO-driven GPU particles, no persistent mapped buffers, deprecated driver with mediocre perf — the entire soil pipeline must be CPU-sided, and buffer upload strategy (orphaning) needs care to avoid GL sync stalls.
- F# byref-like restrictions: Span/byref values can't be captured in closures, async, or most local functions — code that 'looks fine' fails to compile or silently forces copies/boxing when refactored; keep Span usage inside small non-capturing functions. No ref fields means some C#-style zero-copy patterns (self-referential cursors) aren't expressible.
- BEPU determinism is same-machine, same-thread-count, same-interaction-order only; floating-point differs across x64/arm64. Don't build replay/multiplayer features assuming cross-platform determinism.
- BEPU's BufferPool is unmanaged memory with manual lifetime — leaks/UAF are possible from F# just as from C#; wrap acquisition in disciplined helpers and dispose on shutdown.
- Thread oversubscription: BEPU stalls if a worker is preempted; soil jobs + BEPU + render thread + macOS background load on 8–10 cores (only 4–8 are P-cores) can oversubscribe — use one shared dispatcher sized to P-cores minus render/main.
- Per-frame TPL usage (Parallel.For, Task.Run) allocates and introduces scheduling nondeterminism — an easy accidental regression when someone 'just parallelizes' a loop.
- Struct DU pattern matching and large struct copies: F# match on big structs can produce defensive copies; keep hot structs ≤32B and [<IsReadOnly>], or match on discriminator bytes in packed arrays instead of DUs in the innermost loops.
- Amortized systems (settling, remeshing) create visible lag if the dirty queue grows faster than the per-tick budget during heavy digging — need backpressure (coarser settle steps, merge particles early) rather than frame blowout.
- Tiered JIT: first seconds run unoptimized code; without a warmup pass the opening moments stutter and profiles mislead (profile after warmup, or set DOTNET_TieredCompilation=0 when benchmarking kernels).
